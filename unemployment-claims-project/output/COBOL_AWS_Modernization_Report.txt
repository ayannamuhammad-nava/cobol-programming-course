1. High-Level Summary
This report presents a complete technical and business analysis of a legacy COBOL-based unemployment claims system comprising two programs — UNEMPCLM.cbl and GETCLAIM.cbl — and provides a structured roadmap for migrating the system to AWS. The analysis covers business logic, data model, file formats, identified risks, policy-as-code opportunities, and three modernization options with a recommended migration path.
System Overview
UNEMPCLM.cbl — Orchestration and reporting program. Reads batch commands from SYSIN, calls GETCLAIM for data operations, and writes formatted reports to OUTCLAIM (a sequential print file).
GETCLAIM.cbl — Data access layer. The sole program that interacts with the VSAM CLAIMS database. Performs all CRUD operations (Read, Insert, Update, Delete) and returns results to UNEMPCLM via shared Linkage Section memory.
CLAIMS (VSAM KSDS) — The underlying database. An IBM mainframe VSAM Key-Sequenced Data Set storing variable-length records (1-260 characters) keyed by an 8-character period identifier in MMDDYYYY format.
OUTCLAIM.txt — The output report file. A sequential, variable-length formatted print file containing demographic breakdowns of unemployment claims by age, ethnicity, industry, race, and gender.

2. Business Logic Flow
UNEMPCLM.cbl — What It Does
UNEMPCLM is the orchestrator. It acts as the front office of the system — receiving requests, driving the workflow, and producing the human-readable formatted report. It never touches the database directly.
Opens the output report file (OUTCLAIM)
Reads the first command from SYSIN (the batch input stream)
Loops through up to 200 commands per run — calls GETCLAIM, checks return code, writes report header, parses comma-delimited claim data, writes formatted data rows, writes separator line, reads next command, writes blank lines between sections
Closes the output file and terminates
GETCLAIM.cbl — What It Does
GETCLAIM is the data gatekeeper. It is the only program with access to the VSAM CLAIMS file. It receives instructions from UNEMPCLM, performs the database operation, and returns the results.
Command
Operation
Business Behavior
R (Read) — 1 record
Direct keyed lookup
Finds the exact filing period record by its 8-character ID. Returns not-found if no match.
R (Read) — Multiple records
Sequential range scan
Positions at the starting key and reads forward, collecting up to the requested number of consecutive records.
D (Delete)
Read then delete
Reads the record first to capture its data, then permanently removes it. The pre-deletion data is returned to UNEMPCLM for the confirmation report.
I (Insert)
Write then read-back
Writes the new record to VSAM. Immediately reads it back to confirm the insert succeeded before returning.
U (Update)
Read, rewrite, read-back
Reads the existing record, overwrites it in-place with new data, then reads it back to confirm before returning.

4. Identified Issues and Risks
Top 10 Risks — Ranked by Severity
Rank
Risk
Severity
Business Impact
Recommended Fix
1
No cross-category data integrity validation
Critical
Policy decisions and labor statistics derived from data where age totals differ from race totals are silently wrong. No mechanism detects this.
OPA policy engine enforcing sum(age) = sum(race) = sum(gender) before every write. Nightly automated reconciliation job.
2
No authentication or authorization
Critical
Any operator with JCL access can read, modify, or delete any month of claims history. No identity check exists.
Amazon Cognito + IAM roles. Enforced at API Gateway before Lambda runs.
3
No structured audit trail
Critical
No permanent record of who changed what data or when. FISMA and Federal Records Act compliance failure.
Immutable audit_log table in Aurora + CloudTrail. Every write records user_id, operation, timestamp, before/after hash.
4
No transaction support — no rollback
High
A batch run failing midway leaves the database in a partially-updated state with no recovery path.
Aurora ACID transactions. Step Functions checkpointing. Idempotency keys for safe replay.
5
Field size overflow — silent data corruption
High
PIC X(05) fields max at 99,999. COVID-19 peaks exceeded this in many states. Value 125,000 stored as 12,500 with no error raised.
INTEGER/BIGINT columns in Aurora. Configurable maximum threshold with alerting.
6
Updates permanently destroy prior data
High
REWRITE silently overwrites the existing record. No amendment history. Cannot explain why a statistic changed.
Temporal data model in Aurora with effective_from/effective_to columns. Never UPDATE rows — INSERT new versions.
7
VSAM lock-in — zero cloud portability
High
VSAM is IBM z/OS-only. No cloud connector exists. Full data extraction required before any migration.
One-time VSAM export to flat files, then S3, then Aurora. Full ETL pipeline with record-level reconciliation.
8
No encryption at rest or in transit
Medium-High
Demographic claims data stored in plaintext on mainframe DASD. NIST SP 800-53 SC-28 requires encryption at rest.
Aurora KMS encryption at creation. TLS 1.3 at API Gateway. Field-level encryption for sensitive data.
9
Aggregate-only model blocks fraud detection
Medium
No individual claimant records. Cannot detect duplicate claims or fictitious counts.
Normalized relational model with individual claimant records, or federated query model with signed aggregate submissions.
10
Demographic model non-compliant with current standards
Medium
OMB revised SPD-15 in 2024 requiring 7 race categories. Current 5-category model cannot be used for federal reporting.
Extensible demographic_category_ref lookup table. New categories added as data inserts, not code changes.

Option 1 — Minimal-Change Modernization (Rehost)
Run the COBOL programs exactly as they are today, but on AWS infrastructure instead of a mainframe. The code does not change. The batch model does not change. OUTCLAIM.txt still comes out the other end. The mainframe goes away — the COBOL does not.
Key AWS Services:
AWS Mainframe Modernization (Micro Focus runtime on EC2) — runs compiled COBOL binaries natively
Amazon S3 — replaces JES2 SYSIN spool and SYSOUT
AWS Batch — replaces JCL job scheduler
Amazon EventBridge — time-based triggers for recurring batch runs
Amazon CloudWatch — job completion monitoring and ABEND alerting
Micro Focus VSAM on EBS — emulates VSAM KSDS; GETCLAIM file I/O works without modification
Pros:
Fastest path off the mainframe — 12 weeks vs 12+ months for a rewrite
Zero business logic risk — all 20 rules continue working exactly as today
No data migration required — VSAM emulated in-place, decade of history preserved
Immediate cost reduction — mainframe MIPS eliminated
Familiar operational model for the operations team
Cons:
All 20 identified risks remain — field overflow, missing cross-totals validation, no access control, no audit trail
Still dependent on COBOL developer talent pool — shrinking every year
VSAM emulation is a vendor-specific bridge, not a strategic data platform
No cloud-native capabilities — QuickSight, Athena, Glue cannot connect to emulated VSAM
Technical debt is unchanged — every identified problem is deferred, not solved
Best for: Expiring mainframe contract or hardware failure requiring immediate action. Intended as a bridge strategy, not a long-term platform.
Option 2 — Phased Decoupling and API-Led Modernization (Recommended)
Exploit the two natural seams in the codebase — the CALL boundary between UNEMPCLM and GETCLAIM, and GETCLAIM's exclusive ownership of VSAM — to replace the system incrementally using the Strangler Fig pattern. At no point is the entire system offline.
Phase Structure:
Phase A — Data Layer (Weeks 1-9): VSAM exported, Aurora schema designed and loaded, nightly sync established. Aurora is a read-only mirror — mainframe remains system of record.
Phase B — API Layer (Weeks 10-21): Lambda functions replace GETCLAIM logic. A thin COBOL stub translates UNEMPCLM's existing CALL into an HTTP request. UNEMPCLM.cbl does not change a single line.
Phase C — Orchestration Layer (Weeks 22-38): UNEMPCLM replaced by Step Functions. SQS replaces SYSIN. PDF and QuickSight replace OUTCLAIM.txt. OPA policy engine deployed for R15-R20.
Phase D — Decommission (Weeks 39-44): Parallel run complete. Mainframe retired. VSAM archived to S3 Glacier.
Key AWS Services:
Amazon Aurora PostgreSQL — replaces VSAM; normalized schema with temporal history and integer count columns
AWS Lambda (x7) — GetByKey, GetRange, Create, Update, Delete, Validate, GenerateReport
Amazon API Gateway — REST API contract between orchestration and data layers
AWS Step Functions — replaces UNEMPCLM batch loop; stateful, resumable orchestration
Amazon SQS — replaces SYSIN 200-command limit; unlimited capacity
Amazon Cognito — user authentication and group-based role assignment
OPA on Lambda — policy-as-code engine for all 20 business rules
Amazon QuickSight — interactive demographic dashboards
Amazon S3 — JSON output, PDF reports, input archival
Amazon EventBridge — scheduled triggers and nightly integrity checks
Amazon CloudWatch + CloudTrail — full observability and immutable audit logging
Amazon RDS Proxy — connection pooling between Lambda and Aurora
Pros:
Risk is contained to each phase — rollback at any phase boundary is straightforward
Each phase delivers independent production value — REST API available at month 5
UNEMPCLM never needs to be deeply understood — replaced last after data and API layers are proven
Natural seam exploitation — the CALL boundary is exactly the right decoupling point
Missing business rules (R15-R20) introduced in Phase C with proper policy infrastructure
Cons:
The COBOL stub is bespoke complexity — must handle the variable-length OCCURS 1 TO 200 Linkage Section exactly
Two systems in production simultaneously for months — operational overhead is real
OUTCLAIM.txt consumers see no change until Phase C (month 6+)
The 200-command limit and ABEND pattern survive into Phase B
Best for: Operational continuity requirement, incremental risk tolerance, organizations building AWS capability progressively.
Option 3 — Full Cloud-Native Rewrite
Discard both COBOL programs entirely and rebuild the unemployment claims system from scratch as a cloud-native application. The business logic, data model, and operational model are all redesigned — informed by the existing system but not constrained by its limitations.
Pros:
All 20 risks from the risk review are fully addressed — not deferred, not partially mitigated
No COBOL dependency — maintainable by any developer familiar with modern languages
Data model built correctly from the start — temporal history, geographic dimension, extensible categories
Policy-as-code is a first-class citizen — compliance team can read and own the rules
Full observability from day one — CloudWatch, CloudTrail, structured logs, integrity alarms
Strategic platform for the next 20 years — extensible without fundamental redesign
Cons:
Highest risk of business logic regression — two decades of operational knowledge must be re-discovered from COBOL source
Longest timeline before any production value — approximately 12 months
Highest upfront capital investment of the three options
All OUTCLAIM.txt consumers must change their workflow simultaneously
Best for: Strategic platform investment, regulatory compliance requirement, long-term maintainability priority.
Recommendation
Option 2 (Phased Decoupling) is the recommended path, with Option 3 as the stated end state.
The CALL boundary between UNEMPCLM and GETCLAIM is a genuinely clean seam — the Strangler Fig pattern works best when a natural interface exists, and this one does.
The data layer (VSAM) is the highest-risk element and Option 2 addresses it first — fixing field overflow, enabling geographic dimension, and creating temporal history before any application changes.
Phase B delivers a REST API at month 5, not month 12 — 7 months faster than Option 3.
Option 1 does not fix anything — for a government statistical system with no access control, no audit trail, and no cross-totals validation, rehosting is not a viable 5-year strategy.
Phase C of Option 2 and Option 3 converge architecturally — the difference is sequencing and risk distribution, not destination.

Key Architecture Decisions
Decision
Rationale
Replaces
Aurora PostgreSQL over DynamoDB
Claims data is highly relational — period to demographic counts is a one-to-many relationship requiring joins and aggregates. SQL is the natural query language.
VSAM KSDS
